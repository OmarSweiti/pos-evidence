**Runtime change: yes.** `pos-hardware` gains the emulated network printer, behind an off-by-default `emulator` feature, plus `just printer-emulator` to run it. This validation runs it, at the PR head, the way a developer will: through 1.7.10's driver over real TCP, as the committed profile files say each device behaves, under every scripted fault, and against the third-party emupos for the same status bytes and the same page.

**Setup**
- **Code:** PR head `6b6c692` with a clean tree. It holds 1.7.12's emulator (`6fab282`) and the test fix this validation found, merged with `development` after #274. No database is involved, because 1.7.12 touches none.
- **Harness:** a throwaway program outside the repository, linked against this head's `pos-hardware` (with `emulator`) and `pos-domain` through a scratch worktree of the head. It starts each emulator from a committed profile file and drives it with `NetworkPrinter`, or with raw bytes where the point is what the device refuses.
- **The developer's tool:** `just printer-emulator epson-tm-t20iii-ethernet-80mm posiflex-cr-4000-g2`, run in the worktree exactly as documented, printed to by the same driver.
- **Third-party emulator:** **emupos 0.4.0** as an **Epson TM-T20III**, wheel sha256 `d41f15caa2b286e7303b12c4bdcb02dc395c75553479d02b20566e2bacc2bb9a`. It ran in a throwaway `python:3.13-slim` container, ports published on `127.0.0.1` only, started with no receipts.
- **Mutants:** run in the same scratch worktree, so the repository was never edited.
- **Screenshots:** headless Chrome with a throwaway profile, each page rendered from the run's own files.
- **Data:** synthetic only.

**Found by this validation, and fixed in this PR**
- **A mutant survived.** With the `return` after "the profile does not know its `raster_max_rows`" removed, all 106 tests passed. The test that claimed the case used the Bixolon file, which also leaves its framing unknown, and the framing is checked first, so the limit's guard was never reached. The comment said "does not know its limit", but the code under test was the framing check. `test(hardware): an unknown raster limit, alone, prints nothing` adds the isolating case: the TM-T20III's file with only its limit unknown. That mutant is the fourth above, and it is now caught.

**Not validated here, and why**
- **The golden comparison.** `emulated_printer_renders_every_golden_to_its_committed_png` needs 1.7.5's seven committed goldens. 1.7.12 is partially delivered, as its `Full-step status:` marker says, and the frontier does not count it as complete.
- **Any physical device.** None is bought before milestone 5.8.
- **A real drawer.** Both seeded drawer files leave their pin unknown, so the emulator opens nothing for them and says so (step 11). Step 12's drawer model is the harness's, not a sourced fact.
- **Windows.** `just printer-emulator`'s PowerShell body was not run here, and no CI job runs the recipe on any platform. The emulator's tests do run in CI.
- **The register app was not launched.** Nothing the register ships enables the emulator, and the register does not link `pos-hardware` yet.
